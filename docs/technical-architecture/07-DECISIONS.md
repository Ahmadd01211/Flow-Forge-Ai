# 07 — architectural decision register

Status of every decision: proposed for approval. Stack choices explicitly required by the user remain fixed; comparisons explain tradeoffs rather than proposing to substitute a different stack. Reconsideration means gather evidence and write a new ADR, not automatically add the alternative.

| ID / decision | Why appropriate now | Realistic alternatives and tradeoff | Reconsider when |
|---|---|---|---|
| D01 Modular monolith + worker processes | One domain/schema, simple transactions, independently sized runtime pools; small team can understand ownership | Microservices add network contracts, distributed transactions, deployments and tracing. One web process running everything couples latency and failure | A module has a separate team, independent release/security boundary and measured scale bottleneck |
| D02 FastAPI is sole business authority | Python runtime and HTTP contracts share rules; Next.js focuses on UI | Next.js BFF/Server Actions can be useful but duplicate mutation paths/authorization if both own business rules | A concrete server-side composition need cannot be met by existing API; any BFF remains an adapter |
| D03 Server Components + narrow client features | Initial reads/layout on server, canvas/forms interactive; less client bundle and clearer secret boundary | Entire SPA simplifies one mental model but ships more JS; fully server-rendered UI cannot support editor interactions alone | Measured hydration/interaction performance suggests boundary changes |
| D04 Same-origin reverse proxy + opaque sessions | Simple cookies/CSRF, immediate revocation and one auth authority | Browser JWT adds refresh/revocation complexity; OIDC is valuable for SSO but adds identity integration work | Public third-party API/mobile clients need scoped tokens, or enterprise SSO becomes a requirement |
| D05 PostgreSQL + SQLAlchemy/Alembic | Durable transactions, FK ownership, locking and schema evolution fit definitions/runs/ledger | Document DB simplifies graph JSON but complicates relational permissions/atomic accounting; SQLite fine for demos, wrong concurrency model for runtime tests | Measured read/volume needs justify replicas/partitioning; not merely because SaaS may grow |
| D06 Scoped services + composite FKs; RLS deferred | Explicit ownership paths and testable worker/API rules without pooled tenant-session setup | RLS adds defense in depth but must cover workers/admin/migrations and connection context safely; schema-per-tenant increases operations | Enterprise isolation requirements or additional SQL consumers justify implementing/testing RLS end to end |
| D07 JSONB graph snapshot as authority | Easy atomic save/version, bounded MVP graph; no dual editable representation | Normalized node/edge tables improve cross-graph queries but add synchronization/joins; event-sourced graph edits add replay complexity | Real queries require node-level indexing or collaborative editing beyond whole-draft revisions |
| D08 Mutable drafts + immutable test/published versions | Test-before-publish works; runs always reference exact config; history remains inspectable | Running mutable drafts makes reproduction ambiguous; publishing every test pollutes workflow availability | Test snapshot volume needs retention policy, or collaborative branching requires separate draft histories |
| D09 Typed DAG with bounded mappings | Cycles/dependencies/branch semantics understandable; pure validation is testable; no executable user expressions | Arbitrary code/loops increase sandboxing and termination risks; general expression DSL is a programming language to secure | Repeated real use cases need bounded loops/expressions, after explicit isolation and versioning design |
| D10 PostgreSQL scheduler; Celery/Redis delivery | Required stack supports bounded jobs; scheduling state survives broker/worker loss | Celery Canvas/chords are convenient task composition but don't replace domain ownership/budget/state rules; Temporal supplies durable orchestration with another platform | Durable timers, long-running approvals or complex compensation dominate and custom recovery cost becomes significant |
| D11 Transactional outbox + queued-work reconciliation | Closes database/dispatch gap and recovers published-but-lost broker work | Direct DB commit then `.delay()` can lose accepted work; broker-only truth loses domain state; CDC relay adds infrastructure | Outbox polling/DB contention is measured bottleneck; then evaluate CDC or dedicated delivery service |
| D12 Leases/fencing/checkpoints + conservative unknown outcomes | Prevents duplicate state commits, preserves successful work and avoids blind provider recharges | Broker task IDs/late ack alone cannot fence effects; blindly rerunning maximizes apparent completion but risks duplicate cost/effects | A specific provider/tool supports reliable idempotency/receipt lookup that enables safe replay |
| D13 Bounded agent loop task, no blocking child tasks | Simple provider/tool sequence; per-call checkpoints allow recovery; loop never holds HTTP request | Per-turn Celery task adds scheduling/checkpoint orchestration; unbounded loops risk stalled pools | Long agent sessions exceed short runtime caps or finer scheduling fairness is measured as necessary |
| D14 One real provider adapter + deterministic fake | Small actual boundary normalizes capabilities, cost and results; fake enables cheap tests | Universal multi-provider framework creates unsupported capability promises; hardcoded provider calls scatter logic and impede tests | A second real provider/customer requirement exists; extend only proven differences |
| D15 Atomic budget reservations and uncertain holds | Concurrent calls cannot all spend same remaining allowance; unknown charge is visible | Post-hoc accounting allows overspend; Redis-only counters drift on loss; estimated-only charts mislead users | Provider billing APIs permit better reconciliation, or billing-grade settlement is required |
| D16 Trusted installed tools + narrow immutable grants | No user code upload, explicit scopes and destinations; UI permissions map to enforcement | Arbitrary HTTP/code/SQL tools appear flexible but create SSRF, execution and exfiltration risks | Validated customer need plus completed sandbox/egress/approval design |
| D17 Encrypted DB credentials, separate mounted key | Practical local secret storage and rotation without new managed infrastructure | Environment-only secrets cannot naturally support workspace rotation; external vault/KMS improves key controls but adds service dependencies | Production compliance, multi-operator access or key separation warrants managed KMS/secrets store |
| D18 Poll ordered persisted events first | Simple authorization/reconnect, fits MVP run durations and low traffic | SSE improves update latency but adds stream/proxy/reconnect operations; WebSockets add bidirectional complexity not needed yet | Poll load/latency measurements justify SSE; keep same event cursor contract |
| D19 Small maintenance process for relay/recovery | Two short loops, shared deployment and diagnostics, no new scheduler service | Separate relay/reconciler pools isolate scaling but add operations; Celery Beat alone still relies on broker delivery for recovery | Maintenance work interferes with delivery/recovery objectives or independent ownership is necessary |
| D20 No external writes/human approvals in MVP | Honest capability boundary; avoids consequential side effects without an approval product | Enabling writes with an instruction warning provides no enforceable approval; building approval engine early expands scope | First write integration is selected and authorization, human approval, idempotency/receipts and cancellation semantics are designed |
| D21 Bounded Postgres artifacts initially | Small JSON/text inputs/results stay transactionally manageable; encrypted access remains in one deployment | Object storage is better for large binary payloads but introduces uploads/ACL/lifecycle/backup coordination | Payload or retention volume becomes costly; add an artifact-store adapter and object storage then |
| D22 Lockfile/contract generation + focused tests | Reproducible builds and fewer repeated handwritten types; small slices give clear verification | Repeated full scans and giant generated frameworks consume time/tokens; blanket snapshots mirror implementation | A recurring defect demonstrates a missing test boundary or tooling need |
| D23 Whole-run retry creates new linked run | Simple audit and immutable historical outcome; no partial rerun pretending to be same execution | Step-level resume/replay offers flexibility but requires dependency invalidation and effect compensation | Users have costly long graphs and an explicit safe partial replay model |
| D24 Fail-fast workflow with explicit active merge | Clear MVP failure behavior; independent active siblings stop boundedly; branch joins deterministic | Continue-on-error and compensation are useful but multiply output/result semantics | Real workflows need partial success and consumers can handle a designed result contract |

## What this intentionally does not generalize

No event-sourcing framework, generic plugin runtime, service mesh, distributed transaction coordinator, custom AI planning language, dynamic code loader or speculative abstraction for five providers. Add ordinary functions and concrete services first; introduce an interface at an actual replaceable boundary, not for every class.

## Approval consequences

Approval accepts these invariants and planned scope, not a claim that security or recovery already works. Each slice must provide evidence. A material change to ownership, effects, execution semantics or stack returns as a focused decision with tests/impact; ordinary file/function naming and small implementation details do not require repeated approval.
