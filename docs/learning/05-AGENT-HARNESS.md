# Agent harness: what it does today

The harness is the controlled path between a published agent and a model or tool. It is not a free-form script runner. A workspace owner or admin first approves a reviewed tool in the Tool Registry. An editor may select that tool in an agent draft. Publishing freezes the selected tool keys into an immutable version. At run submission, the API checks that every key is still installed; the worker checks again immediately before a call. Revocation therefore blocks new runs and subsequent tool calls.

For OpenAI GPT-5 Mini, the worker sends only the version's selected function definitions to the Responses API. It uses `store: false` and replays response items and function outputs for the next turn. The harness limits model iterations, tool calls, elapsed time, transcript size, and measured spend. It checks cancellation before each turn and tool call. Tool handlers receive bounded JSON, and errors become a small error code that the model can react to. The two initial handlers have no network, filesystem, or credential access.

PostgreSQL owns the run state. Celery delivers a run ID; the database claim token prevents duplicate workers from finalizing the same run. Every model turn and tool action adds a metadata-only event to `agent_run_event`. Event order and status appear in the Runs screen. Inputs, outputs, credentials, model reasoning, and tool arguments stay out of the trace. Run inputs and final outputs remain encrypted in `agent_run`.

The current worker treats a crash after any model call may have begun as an uncertain outcome and does not automatically retry it. This avoids duplicate external charges or effects. A run with tools reserves its configured full budget because multiple model turns may consume it. The measured token cost is summed across known turns; if a response is lost, the UI shows an uncertain upper bound rather than a false exact number.

The present agent harness supports local read-only tools and OpenAI GPT-5 Mini tool calling. Gemini agent runs remain single-call. A separate workflow runner now supports immutable linear input/local-tool/result versions with durable queued runs and safe replay of pure local tools. Remote MCP tools inside runs, agent or branch workflow steps, write tools, and external deployments are separate next slices. MCP tools will enter through the same approval and execution checks; remote server descriptions and annotations will not themselves grant permission.

The stateless replay and strict function schema shape follow [official OpenAI function-calling guidance](https://developers.openai.com/api/docs/guides/function-calling) and [Responses migration guidance](https://developers.openai.com/api/docs/guides/migrate-to-responses). The [MCP Python SDK transport documentation](https://py.sdk.modelcontextprotocol.io/client/transports/) informs the planned Streamable HTTP connector.
